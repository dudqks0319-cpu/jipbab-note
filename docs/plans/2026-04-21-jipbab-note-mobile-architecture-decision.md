# 집밥노트 모바일 아키텍처 결정

## 결론

집밥노트는 장기적으로 `진짜 번들형 앱`으로 가는 것이 맞습니다.

현재처럼 `Capacitor 셸 + 원격 웹앱` 구조는 초기 출시 속도에는 유리하지만, 다음 문제가 남습니다.

- 네트워크/배포 상태에 따라 앱 첫 화면 품질이 흔들릴 수 있음
- App Review에서 웹뷰 셸로 보일 위험이 있음
- 카메라, 로그인, 오프라인, 성능 문제를 모바일 앱답게 다루기 어려움

이번에 추가한 `public/index.html + runtime-app-config.json` fallback은 단기 안정화 용도입니다. 장기 전략의 종착점은 아닙니다.

## 권장 방향

### 1단계: 하이브리드 안정화

단기적으로는 다음을 유지합니다.

- Capacitor 기반 앱 셸
- 핵심 라우트는 웹으로 제공
- 번들 fallback 페이지로 잘못된 원격 연결을 방지

이 단계의 목적은 빠른 출시와 운영 검증입니다.

### 2단계: 번들 우선 구조로 전환

중기적으로는 앱이 먼저 로컬 번들 UI를 띄우고, 원격은 데이터/API에만 의존하도록 바꿉니다.

권장 기준:

- 홈, 냉장고, 장보기, 설정, 계정삭제는 번들 우선
- 레시피 목록/상세는 필요 시 원격 데이터 fetch
- 카메라/로그인/외부 링크는 네이티브 친화형으로 정리

즉, 앱이 “웹사이트를 띄우는 셸”이 아니라 “앱 UI를 번들하고 데이터만 원격에서 받는 구조”가 되어야 합니다.

### 3단계: 네이티브 강화

장기적으로는 아래를 검토합니다.

- 바코드: 웹 `BarcodeDetector` 대신 네이티브 플러그인 검토
- 인증: iOS/Android 복귀 흐름이 명확한 네이티브 친화형 OAuth
- 알림: 실제 로컬/푸시 알림
- 오프라인 캐시: 냉장고/장보기 로컬 우선 동기화

## 왜 이 방향이 맞는가

집밥노트의 핵심 경험은 다음 세 가지입니다.

1. 냉장고 재료 관리
2. 내 재료 기반 레시피 추천
3. 장보기 연결

이 세 가지는 모두 “앱처럼 빠르고 안정적이어야” 신뢰가 생깁니다.

웹뷰 셸은 초기 검증엔 충분하지만,

- 화면 로딩
- 앱스토어 심사 인상
- 권한/복귀 흐름
- 네트워크 불안정 상황

에서 한계가 명확합니다.

## 최종 권고

- **단기 출시:** 현재 하이브리드 구조 + fallback + 운영 검증
- **장기 제품 방향:** 번들 우선 앱으로 전환

즉, 지금은 출시를 위해 하이브리드 구조를 쓰되, 제품 방향 결정은 **번들형 앱으로 간다**가 맞습니다.
