# 집밥노트 출시 하드닝 설계

## 목적

집밥노트를 앱스토어 제출 가능한 수준으로 끌어올리기 위해, 현재 출시 blocker를 먼저 제거하고 재료 입력 경험을 초보자 친화형으로 재설계한다.

이번 범위는 다음 네 축에 집중한다.

1. 보안/권한/심사 blocker 정리
2. 재료 카탈로그와 단위 시스템 도입
3. 냉장고 입력 UX를 하이브리드형으로 개편
4. 쿠팡 파트너스 링크 운영 구조 정리

## 핵심 결정

### 1. 재료 입력은 하이브리드형으로 간다

- 기본 흐름은 `대분류 카테고리 -> 세부 재료 선택 -> 수량/단위 입력`
- 목록에 없는 재료는 `직접 입력`으로 저장 가능
- 이유:
  - 초보자는 선택형이 빠르고 실수도 적다
  - 운영 중 누락 재료가 생겨도 입력이 막히지 않는다
  - 이미 존재하는 추천 API와 냉장고 모달 구조를 재사용하기 쉽다

### 2. 단위는 사용자 “표시 방식”과 저장 구조를 분리한다

- 저장은 재료별로 `amountValue`, `amountUnit`, `quantityDisplay`를 유지한다
- 사용자는 설정에서 선호 단위 시스템을 선택한다
  - `metric`: ml / g / L / kg 중심
  - `spoon`: 큰술 / 작은술 / 컵 중심
  - `count`: 개 / 봉 / 팩 / 캔 중심
- 이유:
  - 데이터는 구조화되고
  - 화면은 사용자 눈높이에 맞출 수 있다
  - 레시피/장보기 확장에도 일관성이 생긴다

### 3. 출시 blocker는 UX보다 먼저 처리한다

- RLS에서 `device_id`를 권한 증명으로 계속 허용하는 구조를 줄인다
- 로그인 후 마이그레이션된 데이터는 계정 소유로 고정한다
- 앱 내 계정 삭제 시작점을 추가한다
- 카메라 권한 문구와 iOS/Android 메타데이터를 맞춘다

## 데이터 모델 설계

### 재료 카테고리

기존 대분류를 다음으로 확장한다.

- 채소
- 과일
- 육류
- 수산물
- 유제품
- 냉동식품
- 조미료
- 곡물/면/빵
- 통조림/가공식품
- 음료/기타

### 세부 재료 카탈로그

정적 카탈로그 파일을 새로 둔다.

- 대분류별 대표 재료를 많이 담는다
- 검색용 별칭을 함께 둔다
- 자주 쓰는 기본 보관 방식과 기본 단위를 함께 둘 수 있게 확장 여지를 둔다

예시 구조:

```ts
type IngredientCatalogItem = {
  id: string
  category: IngredientCategory
  name: string
  aliases?: string[]
  defaultStorageType?: IngredientStorageType
  defaultUnit?: IngredientUnit
}
```

초기 버전은 코드 내 정적 데이터로 두고, 나중에 Supabase나 관리 도구로 옮겨도 되는 구조로 만든다.

### 재료 수량 구조

기존 `quantity: string` 단일 필드를 당장 완전히 제거하지는 않는다.

- UI/타입 레벨에서는 구조화 필드를 추가한다
- 저장 직전에는 기존 문자열 호환도 유지한다
- 단계적으로 다음 필드를 도입한다

```ts
amountValue: number | null
amountUnit: IngredientUnit | null
quantityDisplay: string | null
```

이유:
- 현재 카드/레시피/장보기가 `quantity` 문자열에 의존한다
- 한 번에 DB 컬럼을 깨면 회귀 범위가 커진다
- 우선 앱 동작을 유지하면서 구조화 값을 병행 저장하는 편이 안전하다

## UX 설계

### 냉장고 모달

새 입력 흐름:

1. 대분류 선택
2. 세부 재료 검색/선택
3. 직접 입력 토글 또는 선택값 자동 반영
4. 보관 방식 제안
5. 수량 숫자 입력
6. 단위 칩/셀렉트 선택
7. 유통기한 빠른 선택
8. 메모

중요 원칙:

- 처음 보는 사용자도 “무엇을 넣어야 하는지” 즉시 이해할 것
- 텍스트 자유 입력은 숨기지 않되, 기본은 선택형으로 유도할 것
- 수량 필드는 `숫자 + 단위`로 분리해 입력 부담을 낮출 것
- 카드와 목록은 최종적으로 사람이 읽기 쉬운 문자열을 보여줄 것

### 설정 화면

새 항목 추가:

- 단위 표시 방식
- 계정 삭제 요청/탈퇴 시작

기존 알림 토글은 실제 기능과 연결 전까지 “준비 중” 또는 보조 기능 수준으로 명확히 표현을 낮추는 것이 맞다.

## 보안 및 출시 설계

### RLS 방향

목표는 `비로그인 임시 데이터`와 `로그인 계정 데이터`를 구분하는 것이다.

- 비로그인:
  - `user_id is null`
  - `device_id = current_device_id()` 조건으로만 접근
- 로그인:
  - `user_id = auth.uid()` 조건이 우선
  - 마이그레이션 후에는 계정 row가 device-only 경로로 다시 열리지 않게 한다

가능한 방식:

1. 마이그레이션 시 `device_id`를 null 또는 별도 archived 값으로 바꾸기
2. 정책에서 `user_id is null and device_id = current_device_id()` 형태로 guest scope를 명시하기

이번 작업에서는 2번을 기본으로 하고, 필요 시 1번을 추가한다.

### 계정 삭제

앱 내에서 최소한 다음은 제공한다.

- 마이페이지/설정에서 “계정 삭제” 진입
- 삭제 영향 범위 설명
- 확인 후 지원 채널 또는 실제 삭제 API로 연결

가능하면 실제 삭제 API를 붙이고, 어렵다면 최소한 심사 기준을 만족하는 “앱 내 삭제 시작점”을 만든다.

### 카메라 권한

- iOS `NSCameraUsageDescription` 추가
- Android `CAMERA` permission 추가
- 바코드 페이지 문구를 “지원 안 되면 수동 입력” 기준으로 유지

## 쿠팡 파트너스 링크 설계

현재 구조를 다음 우선순위로 정리한다.

1. 세부 재료 전용 파트너스 링크
2. 대분류 대표 파트너스 링크
3. 쿠팡 검색 fallback

운영 방식:

- env는 재료별 소수 핵심 링크 + 카테고리 대표 링크를 받는다
- 코드에는 카탈로그 항목과 카테고리 매핑 규칙을 둔다
- UI에는 `제휴 링크` 배지를 붙인다

추천 초기 카테고리:

- 계란/우유/버터/치즈
- 기본 채소 묶음
- 육류 대표 묶음
- 냉동식품 대표 묶음
- 조미료 기본 세트

## 검증 계획

### 자동 검증

- `pnpm lint`
- `pnpm exec tsc --noEmit`
- `pnpm build`
- `xcodebuild ... iphonesimulator build`

### 수동 검증

시뮬레이터에서 실제 사용자 흐름 기준으로 본다.

1. 냉장고 -> 재료 추가
2. 카테고리 선택
3. 세부 재료 검색/선택
4. 직접 입력 fallback
5. 단위 시스템 변경
6. 저장 후 카드/홈/장보기 반영
7. 로그인/로그아웃
8. 설정/개인정보/지원/계정삭제 시작
9. 바코드/외부 링크/쿠팡 링크

### 경쟁앱 비교 포인트

검증 때 아래 기준으로 본다.

- 입력 속도
- 초보자 이해도
- 데이터 신뢰도
- 외부 링크의 명확성
- 계정/데이터 관리의 안심감
- 냉장고/레시피/장보기의 연결성
